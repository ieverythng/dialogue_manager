Terminology and conversational flow
====================================

This document describes how `dialogue_manager` represents and tracks
conversations between the robot and the humans around it. It is
intended for developers integrating the node into an interaction stack;
the [README](../README.md) covers the ROS API surface.


At a glance
-----------

`dialogue_manager` owns the *bookkeeping* of every conversation the
robot is currently having: who is being talked to, what has been said,
what was generated by the LLM, what the robot uttered out loud. It
sits between three external worlds:

- **ROS4HRI** publishes the people present (voices, groups). The node
  subscribes to `/humans/voices/*` and `/humans/interactions/groups`
  to know who is in the room and who is talking.
- A **chatbot backend** (e.g. an LLM) is consulted via the
  `chatbot/*` actions/services when one is configured. Chatbot
  presence is optional — without one, the node still tracks
  conversations and emits `RAW_USER_INPUT` intents that a controlling
  script can react to.
- A **multi-modal expression world** drives the robot's output. Verbal
  expression is the main channel — markup-stripped text is sent to a
  Say sub-skill (`/tts/say` by default), with per-word feedback
  forwarded as closed captions. The expression markup language lets
  the same utterance synchronously trigger facial expressions,
  gestures, LED effects, gaze, and other action endpoints listed in
  the `markup_libraries` configuration.

Three high-level skills are exposed: `/skill/chat`, `/skill/ask`,
`/skill/say`. They are the primary way another node (a "mission
controller") drives the robot's conversational behaviour.


Core concepts
-------------

### Dialogue

A *dialogue* represents one on-going conversation between the robot
and an interlocutor. It is identified by a tuple `(UUID, role,
interlocutor)` and carries mutable state over its lifetime: a
priority, a state (PENDING / ACTIVE / WAITING_RESPONSE / COMPLETED),
a chronological history of utterances, and (after it ends) a summary.

The *dialogue history* is the chronological list of utterances in the
dialogue. Each utterance is `(timestamp, speaker_id, text)` where
`speaker_id` is either a person ID (can be the interlocutor, or another person,
in a multi-party conversation scenario) or the sentinel `__myself__` for the
robot.

### Interlocutor

An *interlocutor* is who the robot is talking to. It is either a
ROS4HRI **person_id** or a ROS4HRI **group_id** (mutually exclusive).
Each group ID uniquely maps to a current set of person IDs via the
`/humans/interactions/groups` topic.

### Role

A *role* is a named configuration that captures what the robot is
doing in that conversation. It carries:
- a **prompt** conveying the persona, task, and conversational style
  the robot should adopt (e.g. front-desk receptionist, tour guide,
  clinical companion);
- a set of **semantic filters** controlling which symbolic facts from
  the situated world model are injected into the LLM context.

Two roles are predefined and well-known to the system:
- `DEFAULT_ROLE` (`__default__`): generic, open-ended interaction.
  Used when speech arrives unprompted and `enable_default_chat=True`.
- `ASK_ROLE` (`__ask__`): closed-form questions ("what is your
  age?"). Dialogues with this role are excluded from the LLM context
  by default.


How dialogues come into existence
---------------------------------

Dialogues are created in two ways:

### 1. Pro-active — a `/skill/chat` or `/skill/ask` goal

A caller (typically a mission controller) starts a dialogue with an
explicit role. The Dialogue is created in PENDING state and
transitions to ACTIVE once any chatbot attachment has settled. The
caller controls the dialogue's lifetime via the action goal handle.

### 2. Reactive — first utterance from a speaker

When `enable_default_chat=True` and a tracked voice publishes its
first utterance, the `SpeechHandler` auto-spawns a Dialogue
with role `DEFAULT_ROLE` and `interlocutor.person_id=voice_id`.

If the speaker belongs to one or more ROS4HRI groups, a dialogue is
also spawned for each such group, and per-person dialogues are
spawned for every co-member. This way the speaker, the group, and
the silent participants all gain dialogues at the moment someone
speaks for the first time. Group dialogues are observation-only,
they don't attach to the chatbot (the chatbot is a per-person
conversational partner). Per-person dialogues attach to the chatbot
asynchronously when one is configured.


Recording: who hears what
-------------------------

Every utterance lands in **every dialogue that should receive it**,
not just the speaker's own. The rule is symmetric for incoming
speech and outgoing Say:

| Source                          | Lands in                                               |
| ------------------------------- | ------------------------------------------------------ |
| Speech from `alice`             | alice + every group containing alice + each co-member  |
| Say with `person_id=alice`      | alice + every group containing alice + each co-member  |
| Say with `group_id=group_a`     | group_a + every member of group_a                      |
| Say with no addressee           | every active dialogue with a bound interlocutor        |
| Chatbot response in a dialogue  | only that dialogue (chatbot is per-dialogue scoped)    |

For incoming speech, missing dialogues are auto-spawned when
default-chat is enabled. Outgoing Say only records into dialogues
that are already active; if none exist, a one-shot synthetic
`__say__` dialogue is archived directly to disk so the utterance
still leaves a trace.


Dialogue lifetime
-----------------

A dialogue ends when one of the following happens:

- the chatbot backend explicitly closes it (its `Dialogue` action
  completes, typically because the conversation reached a natural
  end);
- the caller of `/skill/chat` or `/skill/ask` cancels the goal (for
  instance because the controller decided the person has left);
- the dialogue's group disperses: `/humans/interactions/groups`
  publishes an empty members list for that group ID;
- the node is deactivated: all active dialogues are finalised
  before `clear_all()`.

Finalisation is a fixed sequence:
1. State moves to COMPLETED, `ended_at` is set.
2. The dialogue is archived in the per-interlocutor history.
3. A **summariser** runs asynchronously in a daemon thread.

The summariser receives `(current_dialogue, prior_dialogues_for_same_
interlocutor)` and returns text stored on `dialogue.summary`. The
built-in default summariser renders the session's utterances as
plain text; an LLM-backed implementation is a future plug-in (a
backend exposing `chatbot/summarize` is the intended hook).


Conversations history (per-interlocutor)
-----------------------------------------

For every person and every group, the node maintains a chronological
list of past dialogues: the **conversations history**. When a
person takes part in a group conversation, that group's dialogue
appears both in the group's history *and* in each member's personal
history (fan-out happens at archive time using
`/humans/interactions/groups` to resolve members).

Histories are persisted to disk under
`~/.ros/dialogue_manager/conversations/{person,group}/<id>.json`.
Persistence is periodic while active (every 30s) and synchronous on
deactivate / shutdown.

**Pre-fill at session start.** When a new dialogue is spawned for a
known interlocutor, the most recent prior dialogue's *summary* is
prepended to the new dialogue's history as a single `__summary__`
utterance, followed by a `__session_break__` marker. A hidden
`session_start_index` ensures these pre-fill entries are excluded
from archival on the next session end, so summaries don't bleed
between sessions.

**LLM context.** When the chatbot backend is consulted, the
conversations history is rendered to a string and pushed as a
`__system__` priming message at dialogue start. ASK-role dialogues
are excluded by default. See [TODO.md](../TODO.md) for the
context-delivery redesign that's still pending.


Priorities
----------

Every dialogue carries a priority (0–255). Goal acceptance uses two
separate gates because dialogue lifetime and audio output are
distinct concerns:

- **Chat / Ask** (a *new dialogue* arriving) require
  `priority > highest active dialogue priority`. Preemption
  semantics: a new dialogue must outrank existing ones.
- **Say** (a *one-shot expression*) requires
  `priority ≥ current expression priority`. Cooperative semantics:
  a Say can speak alongside any active dialogue and preempts an
  in-flight expression of equal or lower priority.

The current expression priority is set while a Say is actively
playing and cleared when it finishes; dialogue priorities reflect
the dialogues currently tracked in the `DialogueManager`.


Skills
------

### Chat

Open a long-lived conversation with a person or group. The caller
specifies the role; when a chatbot is configured, it's queried for
each user turn and the response is spoken back via the Say
sub-skill. When no chatbot is present, the dialogue is a passive
container — user utterances accumulate in its history and the
controlling script handles intent generation via the
`RAW_USER_INPUT` intent published on `/intents`.

### Ask

Specialised Chat for closed-form questions. The robot speaks the
question and waits for an answer:
- With a chatbot: the question is forwarded with an
  `answers_schema`; the chatbot returns schema-shaped answers.
- Without a chatbot: the next user utterance from the addressed
  interlocutor is captured as a free-text answer (5s timeout).

### Say

One-shot utterance. The text (with markup) is sent to the Say
sub-skill at `/tts/say` (configurable via `say_action`); per-word
feedback drives the `~/robot_speech` topic. Closed captions are
published on `~/closed_captions`. The plain text is recorded in the
addressed interlocutor's dialogue (and fanned out to related
dialogues per the table above).


Introspection
-------------

The node publishes a JSON snapshot of its internal state to
`~/debug_state` (`std_msgs/String`, latched). The snapshot is
emitted on-change only (no heartbeat) and includes active
dialogues with full history, archived dialogues grouped by
interlocutor, chatbot status, and the current expression priority.

The `rqt_dialogues` plugin (separate package, same repo) subscribes
to this topic and renders a live two-pane view: a tree of active
and archived dialogues on top, with a scrollable history of the
selected dialogue on the bottom. Recently-updated dialogue boxes
briefly flash to highlight where activity is happening.
